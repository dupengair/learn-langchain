# RTX 4050 (6GB) 硬件环境下的 Qwen3 模型选型分析

> 生成日期：2026-09-20
> 硬件实测环境：RTX 4050 Laptop（6GB 显存）+ i7-13620H + 宿主机 16GB 内存（WSL2 环境）

## TL;DR 结论

| 需求 | 推荐 | 说明 |
|------|------|------|
| 现状（最流畅） | `qwen3-0.6b` | vLLM 下 100+ tok/s，学习 API 流程够用 |
| **主力升级（推荐甜点位）** | **Qwen3-4B 量化版** | AWQ 走 vLLM，或 Q4 GGUF 走 ollama，25-50 tok/s |
| 想跑 8B | 可以，但要换 ollama | Q4_K_M 量化 + GPU/CPU 混合，约 8-15 tok/s |
| 14B 及以上 | 不推荐 | 大部分权重落在内存/磁盘，速度低于 5 tok/s |
| 有 4090 (24G) PC 可用？ | **训推分离**：4090 微调 → 4050 推理 | 见第 6 节，推荐微调目标 4B，上限 8B |
| 还想做成手机端侧聊天 App？ | 1.7B / 4B 的 GGUF 产物 | 8B 仅高配 Android 旗舰勉强，见第 7 节 |
| 宿主机内存 16GB → 32GB？ | 推理解锁 14B / 30B-A3B MoE，微调上限不变 | 见第 8 节：收益全在 ollama 混合推理路线，质量对比见 8.3 |

**核心结论：8B 能跑，但不是用现在的 vLLM 路线，而是用 ollama（或 llama.cpp）的量化 + 混合推理路线。日常性价比最高的是 4B 量化版。**

## 1. 实测硬件盘点（有几个关键坑）

```
GPU:  NVIDIA GeForce RTX 4050 Laptop GPU
      总显存 6141 MiB，当前已占用 1237 MiB（Windows 桌面/显示器占用）
      → 实际可用于推理的显存 ≈ 4.7 GB，不是满 6GB
CPU:  i7-13620H（10 核 16 线程，WSL2 内可见 8 逻辑核）
内存: 宿主机 16GB，但 WSL2 默认只分到 7.8GB（可用约 5.3GB），swap 4GB
驱动: CUDA 12.8
```

两个必须注意的坑：

1. **显存不是满 6GB**：笔记本直通模式下 Windows 桌面合成器先占掉约 1.2GB，所有显存预算要按 **4.7GB** 算。
2. **WSL2 内存只有 8GB**：宿主机的 16GB 默认被 WSL2 拿走一半。这对后面"8B 混合推理"影响很大，建议在 Windows 用户目录下创建 `C:\Users\<你>\.wslconfig` 调大：

   ```ini
   [wsl2]
   memory=12GB
   swap=8GB
   ```

   改完在 PowerShell 里 `wsl --shutdown` 重启生效。

## 2. 显存需求怎么算

总显存占用 ≈ **权重 + KV cache + 运行开销（约 0.5~1GB）**

### 2.1 权重体积 = 参数量 × 每参数字节数

| 精度 | 每参数字节 | 说明 |
|------|-----------|------|
| BF16/FP16 | 2.0 | vLLM 默认，质量无损 |
| INT8/Q8 | ~1.05 | 质量几乎无损 |
| INT4 (AWQ/GPTQ/Q4_K_M) | ~0.55-0.6 | 6GB 卡的现实选择，质量略降 |

### 2.2 Qwen3 各规格的权重体积

| 模型 | 参数量 | BF16 | INT4 量化 |
|------|--------|------|-----------|
| Qwen3-0.6B | 0.6B | ~1.2 GB | ~0.5 GB |
| Qwen3-1.7B | 2.0B | ~3.4 GB | ~1.3 GB |
| Qwen3-4B | 4.0B | ~8.0 GB | ~2.8 GB |
| Qwen3-8B | 8.2B | ~16.4 GB | ~5.6 GB |
| Qwen3-14B | 14.8B | ~29.6 GB | ~8.7 GB |

### 2.3 KV cache（按 Qwen3 的 GQA 架构，FP16 计算）

- Qwen3-0.6B / 1.7B（28 层 × 8 KV 头 × 128 维）：约 **0.11 MB/token** → 4K 上下文 ≈ 0.45GB，8K ≈ 0.9GB
- Qwen3-4B / 8B（36 层 × 8 KV 头 × 128 维）：约 **0.147 MB/token** → 4K ≈ 0.6GB，8K ≈ 1.2GB，16K ≈ 2.4GB

**上下文长度是显存大头**，6GB 卡上不要开长上下文。

## 3. 6GB 卡适配总表（按实际可用 4.7GB 评估）

| 方案 | 权重+KV+开销 | 可行性 | 预期生成速度* |
|------|-------------|--------|--------------|
| 0.6B BF16 @ vLLM（现状） | ≈ 2.9 GB | ✅ 轻松 | 100+ tok/s |
| 1.7B BF16 @ vLLM | ≈ 5.1 GB | ⚠️ 勉强，上下文限 4K | 30-50 tok/s |
| 1.7B AWQ @ vLLM | ≈ 3.0 GB | ✅ 可行 | 50-70 tok/s |
| **4B AWQ @ vLLM** | ≈ 4.8 GB | ⚠️ 临界可行，上下文限 4-6K | 25-40 tok/s |
| **4B Q4 GGUF @ ollama（全进 GPU）** | ≈ 3.5 GB | ✅ **甜点位** | 35-50 tok/s |
| 8B BF16 @ vLLM | ≈ 18 GB | ❌ 完全不可能 | — |
| 8B AWQ @ vLLM | ≈ 7.0 GB | ❌ 超出可用显存 | — |
| **8B Q4 GGUF @ ollama（GPU+CPU 混合）** | GPU 放约 4GB + 内存约 2GB | ⚠️ 可跑但慢 | 8-15 tok/s |
| 14B Q4 GGUF @ ollama | 大半在内存/磁盘 | ❌ 不推荐 | 3-6 tok/s |

\* 速度估算依据：RTX 4050 Laptop 显存带宽约 192 GB/s，token 生成速度 ≈ 带宽 ÷ 常驻 GPU 的权重体积；落到 CPU 的部分受双通道 DDR5 带宽（约 50-60 GB/s）限制。数值为量级估算，实际取决于量化方式与上下文长度。

## 4. 8B 专项分析：为什么 vLLM 跑不了，ollama 可以

### vLLM 路线（不可行）

vLLM 是**纯 GPU 推理引擎**，所有权重必须装进显存：

- BF16：16.4GB，超出可用显存 3 倍多，直接启动失败
- AWQ（`Qwen/Qwen3-8B-AWQ`）：5.6GB 权重 + KV cache + 开销 ≈ 7GB，仍超过 4.7GB
- vLLM 虽有 `--cpu-offload-gb` 参数，但它是逐层搬运、极慢，且需要等量系统内存——WSL2 只有 8GB，实际不可行

### ollama / llama.cpp 路线（可行）

- `Qwen3 8B` 的 Q4_K_M 量化约 5.1GB，运行时自动把放得下的层放 GPU、其余放 CPU（mmap 从磁盘映射，不吃满内存）
- 速度约 8-15 tok/s：慢，但逐字流式输出时体感可接受
- **质量提升巨大**：8B 相比 0.6B 在指令遵循、代码生成、结构化输出上完全不是一个档次，对学习 Agent/工具调用类任务尤其明显

### LangChain 代码零改动

ollama 自带 OpenAI 兼容端点，只需要改 `.env`：

```bash
API_KEY="ollama"
BASE_URL="http://localhost:11434/v1"
MODEL="qwen3:8b"
```

现有所有 `test_*.py` 脚本不用改一行。

## 5. 分场景推荐

| 场景 | 推荐 |
|------|------|
| 快速验证 LangChain/LangGraph 流程、频繁迭代 | 留在 `qwen3-0.6b`（vLLM） |
| 想要"像样的"对话/代码质量，保持 vLLM 路线 | `Qwen/Qwen3-4B-AWQ`（启动参数见下） |
| 想跑 8B，接受约 10 tok/s | 装 ollama → `ollama run qwen3:8b`，改 `.env` |
| 长上下文任务 | 本地 6GB 卡都吃力，任何模型上下文建议控制在 4-8K |

### 4B AWQ 走 vLLM 的参考启动参数

```bash
vllm serve Qwen/Qwen3-4B-AWQ \
  --port 8000 \
  --max-model-len 6144 \
  --gpu-memory-utilization 0.92
```

`--max-model-len` 必须显式压低，否则默认按模型上限分配 KV cache 会 OOM。

### 补充说明

- 2025 年 7 月后 Qwen 官方还发布了 **Qwen3-4B-Instruct-2507 / Qwen3-4B-Thinking-2507**（非思考/思考两个独立版本），能力显著强于原版 4B，同样有 AWQ/GGUF 量化，优先选 2507 版。
- 原版 Qwen3 小模型默认带 `<think>` 思考输出，质量差且吃 token；教学脚本里可通过聊天模板参数 `enable_thinking=False` 关闭，或 2507-Instruct 版本身不带思考。

## 6. 跨设备工作流：4090 (24G) 训练 → 4050 (6G) 推理

> 场景：手头另有一台 4090 24GB 的 PC，能否在上面微调更大的模型，再拿到本笔记本跑推理？

**答案：可行，而且是社区标准玩法（训推分离）。**

成立的核心逻辑：**推理端的硬件需求只取决于最终产物的体量（参数量 × 精度），与它在哪训练、用什么方式训练完全无关。** 只要微调后的模型量化后体量落在本文第 3 节适配表的可行区间内，笔记本就能跑。

### 6.1 4090 24GB 的微调能力边界

三种微调方式的显存构成不同：

| 方式 | 显存构成 | 24GB 实际能力 |
|------|---------|--------------|
| 全参微调 | 权重 + 梯度 + Adam 状态 ≈ 16 bytes/参数 | 上限约 1.5-2B（4B 要 ~64GB） |
| LoRA（BF16 底座） | 底座 2 bytes/参数 + 很小的 adapter | 4B 轻松；8B 临界可行（batch 1 + 短上下文） |
| QLoRA（4bit 底座） | 底座 ~0.55 bytes/参数 + adapter + 分页优化器 | **8B 轻松（~12GB）；14B 可行（~16GB）；32B 短上下文勉强** |

按模型逐档对照（24GB 卡、小 batch + 梯度累积 + gradient checkpointing）：

| 模型 | 全参微调 | LoRA | QLoRA | 笔记本端可部署性（量化后） |
|------|---------|------|-------|--------------------------|
| 0.6B / 1.7B | ✅ | ✅ | ✅ | ✅ 轻松 |
| 4B | ❌ | ✅ 轻松 | ✅ | ✅ 甜点位（25-50 tok/s） |
| 8B | ❌ (~130GB) | ⚠️ 临界 | ✅ 轻松 | ⚠️ ollama Q4，8-15 tok/s |
| 14B | ❌ | ❌ | ✅ | ❌ 大半落在内存 |
| 32B / 30B-A3B | ❌ | ❌ | ⚠️ | ❌ |

**关键结论：可训练的上限（QLoRA 到 14B/32B）远高于笔记本可流畅推理的上限（4-8B）。瓶颈在笔记本端，所以选微调目标时应按第 3 节的推理适配表倒推——4B 是最佳微调目标，8B 是上限。在 4090 上微调 14B 再拿到笔记本跑没有意义。**

训练耗时量级：4090 上 8B QLoRA 约 2000-4000 tokens/s，10 万 token 量级的数据集几分钟到十几分钟一轮 epoch，教学级微调毫无压力。

### 6.2 产物如何回到笔记本：adapter → merge → 量化 → 传输

LoRA/QLoRA 的直接产物只是 adapter（几十~几百 MB），需要四步变成笔记本可部署的模型：

```
4090 PC                                     笔记本 (4050)
─────────────────────────────────          ─────────────────
QLoRA 训练
  └→ adapter.safetensors (~200MB)
merge（把 adapter 合回底座，先反量化到 BF16）
  └→ merged 模型 BF16 (~8GB / 4B)
量化（二选一）
  ├→ AWQ / GPTQ (~2.8GB)  ──┐
  └→ GGUF Q4_K_M (~2.6GB) ──┤  局域网 scp/samba 传输
                             └→  vLLM 跑 AWQ（4B AWQ 参考第 5 节参数）
                                 或 ollama 跑 GGUF（.env 改 BASE_URL）
```

体积变化示例（以微调 Qwen3-4B 为例）：adapter ~200MB → merged BF16 ~8GB → **最终拷到笔记本的只有 ~2.6-2.8GB**，局域网传输几十秒。

### 6.3 工具链推荐

| 环节 | 推荐工具 | 说明 |
|------|---------|------|
| 训练 | **Unsloth** | 单卡 24GB 显存效率最高，QLoRA 一等公民，官方支持 Qwen3 系列， Notebook 式上手 |
| 训练 | LLaMA-Factory | 中文文档、配置化、有 WebUI，不想写训练代码时用它 |
| merge | Unsloth 自带 / PEFT `merge_and_unload()` | QLoRA 需先反量化再合并 |
| 量化 → vLLM | AutoAWQ | 输出 AWQ 权重给 vLLM |
| 量化 → ollama | llama.cpp 的 `convert_hf_to_gguf.py` + `llama-quantize` | 输出 GGUF 给 ollama |

### 6.4 注意事项（容易踩的坑）

1. **Chat template 必须一致**：微调数据要套用与底座模型相同的 chat template（如 Qwen 的 ChatML 格式），推理端（ollama/vLLM）也要用同一套模板，否则效果会明显变差。推荐直接微调 **Instruct 版**而非 base 版，减少这一层的不确定性。
2. **QLoRA 的二次量化损失**：4bit 底座训练 → 反量化合并（BF16）→ 再量化（AWQ/GGUF），两次量化有一点质量损失，实践上可接受。若追求质量，用 BF16 底座的 LoRA 训练 8B 以内模型可避免，代价是显存要求更高。
3. **merge 后的模型是完整 HF 权重目录**（config + tokenizer + safetensors），vLLM 直接 `vllm serve <目录路径>`；GGUF 则是单文件，放进 ollama 需写一个简短的 `Modelfile`。
4. **先小后大验证全链路**：建议第一次用 0.6B 或 1.7B 走通"训练 → merge → 量化 → 传输 → 部署 → LangChain 调用"全流程（每个环节几分钟），再上 4B 正式微调，避免大模型环节出错浪费训练时间。

## 7. 延伸场景：把微调模型装进手机 —— 端侧本地聊天机器人可行性

> 场景：4090 微调 → 4050 笔记本部署之外，能否再进一步，把模型部署到手机上，做一个完全离线的端侧聊天机器人 App？

**答案：可行，"训在 4090、用在手机"正是端侧 AI 的标准玩法。但要认清一点：手机上没有那 6GB 独显可借，8B 只是旗舰机的天花板，端侧真正的甜点位是 1.7B-4B。**

### 7.1 手机与笔记本的三个本质差别

在第 1 节笔记本盘点的基础上，手机多了三个新约束：

1. **没有显存，只有共享内存**：权重 + KV cache + App 自身全部吃 RAM，还要和系统、其他 App 共享，实际可用 ≈ 总 RAM × 0.5-0.6（比 WSL2 只分一半还苛刻）。
2. **decode 速度上限仍是内存带宽**：旗舰 SoC（骁龙 8 Gen 3 / 天玑 9400 / A17 Pro 以上）LPDDR5X 带宽约 50-68 GB/s，和笔记本双通道 DDR5 同一档——**算法同第 3 节：token 速度 ≈ 带宽 ÷ 常驻权重体积**。所以旗舰手机跑 8B Q4（约 10 tok/s）并不比 4050 笔记本混合推理慢多少，这是反直觉但真实的一点。
3. **算力弱 + 被动散热**：手机 CPU/移动 GPU 的算力远低于 4050 独显，长 prompt 的 prefill（首字延迟）会明显变慢（可能数秒）；持续生成 1-2 分钟触发温度墙降频，速度可再掉 30-50%。

### 7.2 端侧可行性总表

（体积按 GGUF Q4_K_M 口径，与第 4、6.2 节一致）

| 模型 | Q4 量化体积 | 8GB RAM 手机 | 12GB RAM 旗舰 | 16GB RAM 旗舰 | 预期速度（旗舰 SoC）* |
|------|------------|-------------|--------------|--------------|---------------------|
| 0.6B | ~0.5 GB | ✅ | ✅ | ✅ | 60-100 tok/s |
| 1.7B | ~1.3 GB | ✅ | ✅ | ✅ | 30-45 tok/s |
| **4B** | ~2.6 GB | ⚠️ 紧张 | ✅ **甜点位** | ✅ | 15-25 tok/s |
| 8B | ~5.1 GB | ❌ | ⚠️ 勉强 | ⚠️ 可跑，易被杀 | 8-12 tok/s |

\* 冷启动数值；持续生成受温度墙影响会下滑。上下文建议压到 2-4K（KV cache 同样按第 2.3 节算法占内存）。

两个端侧特有的坑：

- **iOS 的单 App 内存墙比 Android 严**：8B Q4（5.1GB 权重 + KV + 运行时 ≈ 6GB+）在 iPhone 上大概率直接被系统杀掉；Android 上 NDK 原生 App 的内存弹性更大，12GB 机型实际可用约 7-8GB。所以 **8B 端侧现实上只存在于高配 Android**。
- **chat template 要随 GGUF 走**：`convert_hf_to_gguf.py` 会把模板写进 GGUF 元数据，端侧 App 里再确认模板选项一致即可（ChatterUI 等支持自定义）——同第 6.4 节第 1 条坑。

### 7.3 落地技术路径（按工程量递增）

**先定量化格式：端侧没有 AWQ 的位置，GGUF 是"笔记本 + 手机"两端通用的最大公约数**——第 6.2 节流程里 merge → GGUF → 量化三步原样复用，同一份 Q4_K_M 文件，笔记本丢给 ollama、手机丢给端侧 App 都能加载，训练端零新增技能。

| 路径 | 做法 | 适合 |
|------|------|------|
| **路径 0：零代码验证** | Q4 GGUF 拷进手机 → 装 **ChatterUI**（Android）/ **PocketPal AI**（iOS+Android）/ **MNN Chat**（阿里系，对 Qwen 友好）→ 本地导入 GGUF 离线聊天 | 半小时走通，先验证微调模型质量再写代码 |
| **路径 1：自有 App（主力推荐）** | Android：**llama.cpp 官方支持 NDK 交叉编译 + JNI**（仓库自带 llama.android 示例），或 **MLC-LLM**（Vulkan/OpenCL 吃移动 GPU）；iOS：llama.cpp 的 **Metal 后端**（iPhone GPU 加速）或 MLC-LLM Swift 包；跨平台可用 Flutter/RN 社区的 llama.cpp 绑定 | 想要自己的聊天 UI、做产品化 |
| **路径 2：NPU 加速（进阶）** | 高通平台走 **Qualcomm AI Hub / ExecuTorch 的 QNN 后端**把模型编译到 Hexagon NPU（W4A16），8B 可到约 20 tok/s 级别且功耗显著更低；iOS 走 Core ML（注意 **MLX 只支持 Mac，iPhone 上不可用**） | 对首字延迟/续航敏感，或非要上 8B；工程量最大，建议路径 0/1 验证价值后再投入 |

补充：Google 的 **MediaPipe LLM Inference API / AI Edge Gallery** 也是 Android 端选项，但以官方支持列表（Gemma 系等）为主，自定义微调模型要走 AI Edge 转换链路，不如 llama.cpp/MLC 直接；ExecuTorch 官方导出示例以 Llama 系列最成熟，Qwen 需参考仓库示例脚本。

### 7.4 微调目标要不要为手机改？——"按推理端倒推"原则的第三次生效

第 6 节的原则是"按推理端最弱设备倒推微调目标"，把手机加进来后这条链变成：

| 部署端 | 天花板 | 甜点位 |
|--------|-------|--------|
| 4050 笔记本 | 8B | 4B |
| 旗舰手机 12GB+ | 8B（勉强） | **1.7B - 4B** |
| 主流手机 8GB | 4B（紧张） | 0.6B - 1.7B |

结论：**聊天机器人的目标终端是手机的话，微调目标直接定 4B（适配旗舰）或 1.7B（覆盖 8GB 主流机）；8B 留给笔记本/PC 当"高质量模式"。** 4090 上同一套工作流可以一次产出 4B 和 8B 两份量化产物——很多端侧产品正是这个形态：App 内提供"标准（4B，手机可跑）/ 增强（8B，仅 PC 端）"双模型切换。

## 8. 内存升级分析：宿主机 16GB → 32GB，上限能提到多少？

> 补充日期：2026-09-29。场景：系统内存翻倍到 32GB，GPU 仍是 RTX 4050 Laptop（6GB，可用约 4.7GB，口径见第 1 节——RTX 4050 Laptop 官方规格就是 6GB GDDR6，**没有 8GB 版本**）。

**先给结论：推理上限能提升（8B → 14B，并且新解锁 30B-A3B MoE 这个甜点）；微调上限几乎不变（瓶颈在显存，不在内存）。收益全部落在 ollama / llama.cpp 混合推理路线上。**

### 8.1 原理：内存升级解锁"容量类瓶颈"，对"带宽类瓶颈"无效

token 生成速度 ≈ 每 token 需读取的权重体积 ÷ 所在介质带宽：

| 介质 | 带宽 | 内存升级后 |
|------|------|-----------|
| RTX 4050 显存 | ~192 GB/s | 容量不变（可用 4.7GB），速度上限不变 |
| 双通道 DDR5 内存 | ~50-60 GB/s | **容量 8GB → 24GB（WSL2），带宽不变** |
| NVMe 磁盘（mmap 换页兜底） | 顺序 3-7 GB/s | 命中率趋近于 0，不再拖后腿 |

由此三条推论：

1. **装不下的模型**（14B、MoE 大模型）→ 内存升级直接解锁，这是"容量类瓶颈"；
2. **已经装得下的模型**（0.6B-8B）→ 速度一个 token 都不会变快，只是更稳、能开更长上下文，因为速度受"带宽类瓶颈"约束；
3. **vLLM 路线零收益**：vLLM 是纯 GPU 引擎（第 4 节），权重必须全进显存，内存再大也帮不上。

前提配置：`.wslconfig` 随之调大（Windows 自身留 8GB）：

```ini
[wsl2]
memory=24GB
swap=16GB
```

### 8.2 推理上限：逐档对照（Q4 GGUF @ ollama 混合推理）

| 模型 | 16GB 宿主机（第 3 节现状） | 32GB 宿主机 | 变化 |
|------|--------------------------|------------|------|
| 4B（~2.6GB 全进 GPU） | 35-50 tok/s ✅ | 35-50 tok/s ✅ 不变 | 权重在显存，与内存无关 |
| 8B（~5.1GB 混合） | 8-15 tok/s ⚠️，上下文限 4K | 8-15 tok/s ⚠️，上下文可开 16K+ | **速度不变**；KV cache 不再和权重抢内存，长上下文解锁 |
| 14B（~8.7GB 混合） | ❌ 不推荐，3-6 tok/s | ⚠️ 可跑，**5-9 tok/s** | **上限解锁**（见下） |
| **30B-A3B MoE（~18.6GB）** | ❌ 装不下 | ⚠️ **10-20 tok/s** | **32GB 升级的核心收益**（见下） |
| 32B dense（~19GB） | ❌ | 极慢 2-4 tok/s | 理论能跑，无实用价值 |

14B 提速的机理：16GB 时 9GB 权重 mmap 进 12GB 的 WSL2，和系统、KV cache 挤在一起，反复从磁盘换页，速度被 NVMe 拖到 3-6 tok/s；32GB 下权重一次载入全程驻留内存，速度回到介质带宽决定的真实水平——GPU 承担约 4GB（≈21ms/token）+ 内存承担约 5GB（≈91ms/token）≈ 9 tok/s。

30B-A3B 为什么能跑（dense 32B 却不行）：Qwen3-30B-A3B 是 MoE 模型，总参数 30.5B 但**每 token 只激活约 3.3B**。把专家权重全放内存、attention 共享部分放 GPU（llama.cpp 用 `--n-cpu-moe`，ollama 对该模型默认如此）之后，每 token 从内存读取的只有约 2GB 激活参数（≈36ms），比 8B dense 的内存读取负担还小——**速度反而接近甚至快过 8B 混合推理**。这类"要容量、不太要带宽"的模型正是内存升级的典型受益者，质量对标同代更大的 dense 模型。推荐非思考版 `Qwen3-30B-A3B-Instruct-2507`，上下文控制在 4-8K。

### 8.3 质量差距有多大？30B-A3B vs 4B vs 0.6B（对话问答与 RAG）

> 先澄清对 MoE 最常见的误解：**模型能力由总参数决定，不由激活参数决定**。30B-A3B 每 token 只激活 3.3B，但知识存储在全部 30.5B 权重里，路由器按 token 挑选专家——"激活 3.3B"意味着它**跑得像 3B 模型一样快**，**不代表它答得像 3B 模型一样差**。官方对它的定位就是对标同代 14B dense。

**结论：0.6B → 4B 是"从经常出错到基本可用"的跨越；4B → 30B-A3B 是"从可用到好用"的跨越——在知识面、复杂推理和抗幻觉上差距明显，且这两个差距在 RAG 场景同样成立。**

#### 对话问答维度

| 能力维度 | 0.6B | 4B | 30B-A3B |
|---------|------|-----|--------|
| 简单指令 / 短问答 | ⚠️ 经常跑偏、复读 | ✅ 基本可靠 | ✅ 可靠 |
| 知识面（无检索时） | ❌ 大量幻觉 | ⚠️ 常识可以，长尾靠编 | ✅ 对标 14B |
| 多步推理 / 代码 | ❌ | ⚠️ 简单可以 | ✅ |
| 结构化输出（JSON / 固定格式） | ❌ 频繁坏格式 | ✅ 简单格式可用 | ✅ 稳定 |
| 多轮长对话不丢指令 | ❌ | ⚠️ | ✅ |
| 工具调用 / Agent | ❌ 参数常错 | ⚠️ 能跑通流程 | ✅ 接近产品级 |

量级参考（官方 Instruct-2507 版、BF16 公开成绩）：MMLU-Pro 约 80（30B-A3B）vs 约 58（4B）；GPQA 约 73 vs 约 60。本机的 Q4 量化会比官方成绩略降 1-3 个点，但不改变排序。

#### RAG 场景专项

先划清边界：**RAG 的检索端（embedding + reranker）与 LLM 无关**，换 LLM 不会提升检索命中率；LLM 决定的是"拿到检索结果之后答得好不好"。差距集中在四件事上：

| RAG 环节 | 0.6B | 4B | 30B-A3B |
|---------|------|-----|--------|
| 忠实度：按检索片段回答而非编造 | ❌ 幻觉主导，经常无视上下文 | ✅ 单片段可靠 | ✅ 强 |
| 多片段综合 / 多跳（答案散在多个 chunk） | ❌ | ⚠️ 两跳尚可，再多就丢 | ✅ |
| 检索不中时拒答 / 说明 | ❌ 几乎必编 | ⚠️ 提示词强调后部分可靠 | ✅ |
| 抽取式结构化回答（带引用 / 字段） | ❌ | ✅ 简单字段可用 | ✅ |

RAG 实验的一个特有陷阱：**评估检索效果（换 embedding、调 top-k、改 chunk 大小）必须用 4B 以上模型**。0.6B 的输出随机性太大，你看到的"效果波动"大部分是生成端噪声而不是检索质量变化，会严重误导调参。教学上 0.6B 只适合跑通管道（本仓库 CLAUDE.md 也明确：不能以 0.6B 的生成质量判断脚本正确性）。

#### 代价：30B-A3B 在 RAG 里的首字延迟

decode 10-20 tok/s 流式可读（8.2 节），但 RAG 的 prompt 天然长（top-k 片段通常 2-4K token），而 **prefill 是计算密集型：30B-A3B 的专家权重落在内存/CPU 上时，4K 上下文的首字延迟可能到数十秒**（4B 全 GPU 是 1 秒级）。缓解手段：上 reranker 精选、收紧 top-k、缩小 chunk，把上下文压到 1-2K；或接受"首字慢、后续流式"。

实践建议一句话：**0.6B 跑通流程、4B 日常 RAG 主力、30B-A3B 当"本地质量天花板"用于真实问答和对照评估**——三档切换仍然只改 `.env` 一行。

### 8.4 微调上限：不变，瓶颈在显存

本机微调（显存算法对照第 6.1 节，可用 4.7GB）：

| 方式 | 笔记本本机微调上限 | 内存 16 → 32GB 的影响 |
|------|------------------|---------------------|
| 全参微调 | ~0.3B（16 bytes/参数） | 无 |
| LoRA（BF16 底座） | 0.6B ✅；1.7B 勉强 | 无，底座权重在显存 |
| QLoRA（4bit 底座） | 1.7B ✅；4B 是 batch 1 + 2K 上下文的极限实验 | batch / 上下文可稍放宽，**模型上限不变** |

训练时底座权重、梯度、激活值全部要在显存里，这部分需求只由模型大小决定，系统内存帮不上；内存变大只是让 paged optimizer、数据加载、pin memory 更从容——**训练过程更稳，不改变"能训多大"**。

至于"32GB 能不能 offload 硬训 8B QLoRA"：权重装得下了，也能跑起来，但每个 step 都要在 PCIe 上来回搬数据，比 4090 慢两个数量级以上，教学上没有价值。**大模型微调继续走第 6 节的 4090 路线，结论不变。**

### 8.5 值不值得升

| 你的目标 | 32GB 值不值 |
|---------|-----------|
| 想本地跑更大的模型（14B / 30B-A3B） | **值**：30B-A3B 是惊喜，10-20 tok/s 可日常流式使用，质量对标 14B（见 8.3） |
| RAG / 长上下文实验多 | 值：8B 上下文 4K → 16K+，KV cache 不再和权重抢内存 |
| RAG 认真评估检索效果 / 要像样的问答质量 | 值：见 8.3——评估必须用 4B 以上，30B-A3B 是本地质量天花板（注意首字延迟） |
| 主要为了微调更大的模型 | 不值：瓶颈在显存，这笔预算应投给 4090 PC（第 6 节） |
| 日常只跑 0.6B-4B | 不值：16GB 已绰绰有余 |

## 9. 一句话建议

**先把 `.wslconfig` 内存调到 12GB；然后装 ollama 跑 `qwen3:4b`（日常主力，35-50 tok/s）和 `qwen3:8b`（要质量时切换，约 10 tok/s）；vLLM + 0.6B 保留做快速迭代。三档切换只改 `.env` 一行。**

**如果有 4090 (24G) PC：直接把微调目标定为 Qwen3-4B（Unsloth + QLoRA），产物量化后拷回笔记本走 ollama/vLLM——训练端随它到 14B，推理端 4-8B 就是天花板，围绕 4B 建工作流最划算。**

**如果还想做成手机端侧聊天机器人：同一条 4090 工作流顺手多产出一个 4B（或 1.7B）的 Q4 GGUF，先装 ChatterUI / MNN Chat 零代码验证，再用 llama.cpp（Android JNI / iOS Metal）做自己的 App——见第 7 节。**

**如果把宿主机内存升级到 32GB：推理端解锁 14B（5-9 tok/s）和 30B-A3B MoE（10-20 tok/s，本次升级的核心收益，`.wslconfig` 调到 24GB）；微调端上限不变（瓶颈在显存），大模型微调仍走 4090——详见第 8 节。**
